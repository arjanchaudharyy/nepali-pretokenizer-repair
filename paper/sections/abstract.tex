\begin{abstract}
Llama-3, Qwen3 and many other open LLMs pre-tokenize text with a regular expression whose word class admits only Unicode letters. Devanagari vowel signs are combining marks, so this regex splits Nepali words at every vowel sign, and current open models that use it spend $2.6$ to $5.8$ times as many tokens on Nepali as on the same text in English. We ask what this means for adapting a model that is already deployed. Merge-based vocabulary extension cannot join the split pieces: for Llama-3 and Qwen3 no number of new merges brings the premium below about $2.2$, and ten released extensions for six Indic and Southeast Asian scripts already end within 4\% of this pre-token floor. We give a small edit to the deployed regex and prove that it changes no token id for text without combining marks or Devanagari characters. With 32{,}000 new merges it brings Nepali to $1.01$ times English. We then ran a pre-registered comparison with continued pretraining of Llama-3.2-1B and Qwen3-0.6B on 1\,GB of Nepali and 1\,GB of English. Our main hypothesis failed: continued pretraining without new tokens gave the best held-out Nepali bits per byte, so extension of either kind was worse than keeping the original vocabulary. A pre-registered Llama rerun with the beginning-of-sequence token in training removes a scoring artifact of our first runs. In it the repair was $0.026$ bits per byte (about 5\%) worse than standard extension on Nepali and slightly better on English; for Qwen it was $0.009$ worse on Nepali. In exchange, the repaired model needs $2.2$ times fewer decoding steps than standard extension for the same Nepali text. We release the tokenizers and code.
\end{abstract}
