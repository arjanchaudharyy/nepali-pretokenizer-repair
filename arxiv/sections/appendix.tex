\section{Repair details}
\label{app:regex}

\paragraph{Regex edit.} For the Llama-3 and Qwen pattern we make two string substitutions. The first replaces \texttt{\textbackslash p\{L\}+} by \texttt{[\textbackslash p\{L\}\textbackslash p\{M\}]+} in the word branch. The second inserts \texttt{\textbackslash p\{M\}} after \texttt{\textbackslash p\{L\}} in the two negated classes, the optional leading character of the word branch and the punctuation branch. Three character classes change:
\begin{center}\small
\texttt{[\textasciicircum\textbackslash r\textbackslash n\textbackslash p\{L\}\textbackslash p\{N\}]?\textbackslash p\{L\}+}\\
$\downarrow$\\
\texttt{[\textasciicircum\textbackslash r\textbackslash n\textbackslash p\{L\}\textbackslash p\{M\}\textbackslash p\{N\}]?[\textbackslash p\{L\}\textbackslash p\{M\}]+}\\[4pt]
\texttt{\textvisiblespace?[\textasciicircum\textbackslash s\textbackslash p\{L\}\textbackslash p\{N\}]+}
$\;\rightarrow\;$
\texttt{\textvisiblespace?[\textasciicircum\textbackslash s\textbackslash p\{L\}\textbackslash p\{M\}\textbackslash p\{N\}]+}
\end{center}
Nothing else in the pattern changes.

\paragraph{Devanagari-only variant.} The variant replaces \pM{} in the three classes by an explicit class of the 34 combining marks of the Devanagari block (U+0900--0903, U+093A--093C, U+093E--094F, U+0951--0957, U+0962--0963). We checked that this class equals the set of \pM{} code points in the block under Python's \texttt{unicodedata} (Unicode 15.0), the \texttt{regex} module and the Hugging Face \texttt{tokenizers} engine. Every other character has the same class membership as in the original regex, so any text without a Devanagari mark is pre-tokenized exactly as before. Across the 204 FLORES-200 devtest files, the general repair changes pre-tokens in 61 languages for both models and the Devanagari-only variant in exactly the ten Devanagari languages. On FLORES Nepali the two variants give identical pre-tokens and identical \RII{} token ids. On a 275\,MB sample of FineWeb-2 Nepali (49{,}462 lines), 24 lines differ, in 47 segments; the marks involved are emoji variation selectors, Kannada, Bengali, Thai and Hebrew signs and one combining candrabindu in romanised text, and the \RII{} token count of those lines is the same under both.

\paragraph{Continued BPE.} At inference BPE applies the lowest-ranked applicable merge first, so the original merges act before the new ones. The extended tokenizer reproduces the training procedure except in two cases: a new merge whose output string is already in the original vocabulary can let an original merge fire again afterwards, and under Hugging Face's \texttt{ignore\_merges} option (set for Llama-3) a pre-token that is itself a vocabulary entry is emitted directly. Neither case affects Proposition~\ref{prop:lossless}. We run merge learning inside the Hugging Face Rust trainer by mapping each base token to a private-use code point; learning $K{=}32{,}000$ merges on 1\,GB of Nepali takes 1.7 to 3.4 minutes per tokenizer.

\paragraph{Scope of Proposition~\ref{prop:lossless}.} The proposition covers ASCII English and code and every script whose normalised text has no combining marks, including most Cyrillic, Han, Hangul and Ethiopic text. It does not cover Devanagari, which changes by design, or text with marks, such as Hindi, Arabic with vowel points, Thai, or Latin written in decomposed form (NFD). The Llama-3 tokenizer has no normalizer, so deployments should apply NFC first; Qwen3's tokenizer applies NFC itself. It also assumes that the regex engine's \pM{} table matches the one used to define $s$; for the Devanagari-only variant we checked this directly. Empirically, \RI{} and \RII{} at $K{=}32{,}000$ give token ids identical to the original tokenizer on all 1{,}012 FLORES devtest sentences in English, Russian and Amharic, for both models, including one Russian sentence with a combining acute that lies outside the proposition.

\section{Proof of Proposition~\ref{prop:lossless}}
\label{app:proof}

\begin{proof}
\emph{Pre-tokens.} The repaired regex differs from the original only in the three classes of Appendix~\ref{app:regex}, and each differs from its original only on \pM{} characters. A regex match on $s$ consults only characters of $s$, and the order of the alternatives is unchanged. Since $s$ has no \pM{} character, both regexes produce the same pre-tokens.
\emph{Merges and vocabulary.} \RII{} differs from the original tokenizer only by appended merges and the vocabulary entries they create, each of which contains a complete code point in U+0900--U+097F. A merge $(a,b)$ applies only where $a$ and $b$ are adjacent symbols of a pre-token, so its output is a contiguous substring of that pre-token's bytes. A vocabulary entry is emitted directly under \texttt{ignore\_merges} only if it equals the whole pre-token. Neither can happen for a pre-token of $s$, because UTF-8 is self-synchronising and $s$ contains no such code point. Each pre-token of $s$ is therefore encoded with original merges and original vocabulary entries only, exactly as by the original tokenizer.
\emph{Ids.} New ids are appended above the original ids, so all ids coincide.
\end{proof}

\section{Training and evaluation protocol}
\label{app:protocol}

\paragraph{Data.} We normalise to NFC, drop documents under 200 characters, remove exact duplicates, and drop every document that shares a whitespace 10-gram with FLORES-200 dev or devtest in Nepali or English. This also covers the Belebele passages, which are FLORES passages~\citep{bandarkar-etal-2024-belebele}, but not its questions or answers. Documents are stored one JSON-encoded document per line. A 30\,MB held-out slice of each language is carved from the cleaned stream before training and never trained on. The 1\,GB of Nepali used to learn merges is taken from the start of the training stream.

\paragraph{Continued pretraining.} Documents are interleaved and separated by the model's end-of-text token; in the main and warm-up runs no BOS token is inserted, and in the Llama BOS-consistent rerun every document is wrapped as BOS, document, end-of-text. Optimisation is identical across arms: sequence length 2{,}048, global batch 256 sequences (0.52M tokens), AdamW ($\beta = (0.9, 0.95)$, weight decay 0.1), gradient clipping at 1.0, 1\% linear warm-up, then cosine decay to 10\% of peak, bf16 autocast with fp32 master weights, on 4$\times$H200. Initialisation is deterministic and there is no dropout, so a second seed would change only the order of training windows and bf16 non-determinism. In the warm-up runs, stage 1 trains the whole tied embedding matrix, old rows included, at $10^{-3}$ on the first 10\% of the stream; stage 2 is a main run started from the stage-1 model.

\paragraph{Evaluation.} Every scored sequence is preceded by one context token (\S\ref{sec:setup}), identically for every arm of a model.
\begin{itemize}
  \setlength\itemsep{0pt}
  \item \textbf{BPB} on the held-out native slices (the first 4\,MB of each) and on FLORES-200 devtest. In the primary byte-matched version, each held-out document is split at whitespace into pieces of at most 2{,}000 bytes and every piece is scored independently, so every arm conditions on the same bytes. Token windows would give \RII{} more bytes of context per scored token. As a secondary metric, whole documents are scored with a sliding window of 2{,}048 tokens and stride 1{,}024.
  \item \textbf{Belebele}~\citep{bandarkar-etal-2024-belebele} \texttt{npi\_Deva} and \texttt{eng\_Latn}, zero-shot, scoring each answer string by its log-likelihood per byte given passage and question.
  \item \textbf{Translation}: FLORES-200 devtest Nepali$\leftrightarrow$English, 5-shot from FLORES dev, greedy decoding capped at 512 new tokens, first output line, chrF++.
  \item \textbf{Generation speed}: UTF-8 bytes generated per second in greedy continuation of FLORES dev Nepali sentences (batch 64, 128 new tokens).
\end{itemize}
Document ids were not stored with the pieces; for the clustered bootstrap we reconstruct them by taking a piece shorter than 1{,}900 bytes to end a document, which gives 484 clusters from 2{,}259 pieces. The held-out slice in fact holds 503 documents (the first 503 of FineWeb-2 \texttt{npi\_Deva} after cleaning, recovered after review); with these true boundaries no interval endpoint moves by more than $0.0001$ and no verdict changes (\url{results/revision/heldout_ne_doc_ids.json}). The margin of 0.01 is 1.3\% of the base Llama model's Nepali BPB and 1.2\% of base Qwen's. The equal-compute checkpoints are scored on BPB only, on the first 1\,MB of each held-out slice (567 Nepali pieces from 111 reconstructed documents).

\section{Premium decomposition}
\label{app:decomp}

We write the premium as
\begin{equation*}
\frac{|T(\text{ne})|}{|T(\text{en})|} = \underbrace{\frac{|P_{\text{rep}}(\text{ne})|}{|T(\text{en})|}}_{\text{base}} \cdot \underbrace{\frac{|P(\text{ne})|}{|P_{\text{rep}}(\text{ne})|}}_{\text{regex factor}} \cdot \underbrace{\frac{|T(\text{ne})|}{|P(\text{ne})|}}_{\text{vocabulary factor}},
\end{equation*}
where $P$ is the tokenizer's own pre-tokenizer and $P_{\text{rep}}$ is the repaired Llama-3 pattern, applied to every tokenizer so that the numerator of the base term is the same for all. The base lies between $0.77$ and $0.80$ because English token counts barely differ. Using one pattern means that Qwen's regex factor also includes its single-digit splitting. The regex factor is $0.99$--$1.02$ for mark-aware tokenizers, $2.77$--$2.79$ for the Llama-3, Qwen and \texttt{cl100k} pattern, $4.06$ for GPT-2, whose pattern puts every run of marks in a pre-token of its own, and $5.01$ for Falcon3. Falcon3's pipeline splits digits after its byte-level step, and its byte-level alphabet writes byte \texttt{0xBE} as \textthreequarters{}, which Unicode classes as a number, so it cuts the vowel sign \texttt{U+093E} inside its UTF-8 encoding. All floors and factors here count pre-tokens of each tokenizer's full pre-tokenizer pipeline; counting its last regex alone, as our audit script first did, understates Falcon3's floor ($3.21$ instead of $3.96$). The decomposition is an accounting identity and does not attribute cause. The regex factor is the room that a better regex creates, which new merges must then fill.

Table~\ref{tab:decomp} shows the factors. For Llama-3 the vocabulary factor is $1.18$, the lowest in the audit: its 128k vocabulary already nearly covers Nepali pre-tokens. For Qwen and \texttt{cl100k} both factors matter. Qwen3.5's word branch is our repaired class with only the leading-character class left unchanged; \citet{land2026smallbugs} reported its change for Hindi.

The merge-learning text ranges from 25\,MB (Amharic) to 361\,MB (Bengali), less than the 1\,GB used for Nepali, so for languages where \RI{} ran out of merges we cannot fully separate the floor from data scarcity; Sinhala and Amharic \RII{} may also be limited by data.

\paragraph{A relaxed merge filter.} The Nepali filter keeps a new merge only if its output contains a complete Devanagari character. Scripts that the base vocabularies cover poorly have characters split into byte pieces, and this filter would drop the first byte-level merge of each such character and every merge built on it (for Sinhala \RII{} on Llama-3, only 13{,}530 of 32{,}000 merges survived). For this sweep we therefore also keep merges whose output is a byte piece of a target-script character. Such merges can fire on other scripts that share those bytes: the lead byte 0xE0 begins every code point from U+0800 to U+0FFF, which covers all Indic scripts and Thai, and a continuation-byte suffix can end code points in other blocks. They cannot fire on ASCII text, which contains no such bytes, and we verified English token ids on all 1{,}012 sentences for every tokenizer. Proposition~\ref{prop:lossless} does not cover these tokenizers, and we did not measure their effect on other non-ASCII scripts. Hindi shares the Nepali script, and Nepali merges also change Hindi tokenization.

\paragraph{Thai and Burmese.} Both are written without spaces between words, so a repaired pre-token can span several words. In practice no \RII{} Thai- or Burmese-script token spans a space in either language. In Thai, 28\% (Llama-3) and 25\% (Qwen3) of \RII{}'s Thai-script tokens cover more than one dictionary word (PyThaiNLP \texttt{newmm} segmentation), fewer than under \RI{} (33\% and 31\%). In Burmese, \RII{}'s tokens average 2.2 and 1.8 syllables, against 1.3 under \RI{} and 5.1 syllables per space-delimited chunk.

\label{app:extras}

\paragraph{Regex alone.} Repairing the regex without adding merges (\RII{}, $K{=}0$) gives $2.61$ for Llama-3 (from $2.58$) and $4.42$ for Qwen3. Under the repaired regex the old merges still tokenize Nepali words in old pieces; the repair only removes the bound that new merges would otherwise hit.

\paragraph{Added tokens.} Table~\ref{tab:added} gives the added-token arm of \S\ref{sec:floor}. Default matching reaches almost \RII{}'s compression and the lowest mark-initial rate, but splits many words at arbitrary points: a fifth of the added-token matches start inside a word and more than a quarter end inside one. With whole-word matching, few strings ever match and the premium returns close to the original.

\input{sections/added_table}

\paragraph{Broken syllables.} A token that starts with a combining mark has certainly split a syllable, but the converse does not hold: a token can also end inside an akshara, for example just before a virama, so these shares are a lower bound on split syllables. Counting only tokens that contain Devanagari, the share that begin with a combining mark rises from 57\% (Llama-3) and 33\% (Qwen3) to 67\% for both under \RI{}, and falls to 15\% and 12\% under \RII{}. The letters-only regex leaves few distinct Nepali pre-tokens, so 5k to 30k merges cover nearly all frequent ones, which is why \RI{} saturates early.

\paragraph{Equal compute and training time.} At \RII{}'s final step count, the \RO{} checkpoint of the main runs, whose learning rate had not yet decayed, is already better than the final \RII{} model by $0.060$ $[0.056, 0.063]$ on Llama and $0.053$ $[0.049, 0.057]$ on Qwen. The \RI{} checkpoint at that step is better by $0.006$ $[0.003, 0.008]$ on Llama and level on Qwen ($0.0000$ $[-0.0021, +0.0019]$; final \RI{} is better than final \RII{} by $0.009$ on the same pieces, so on Qwen all of \RI{}'s advantage arrives in its last 192 steps, over which its learning rate falls the last 16\% of the way to its floor). These are scored on the first 1\,MB of held-out text with the registered prefix, so the Llama values carry the BOS artifact of \S\ref{sec:cpt}; no such checkpoints were scored for the rerun. Measured training time fell by only 3\% (Llama) and 11\% (Qwen) relative to \RI{}, in runs that shared GPUs with evaluation jobs.

\paragraph{Warm-up runs.} Training only the embedding matrix first leaves \RO{} where it was ($0.471$ after the training separator) and improves \RII{} from $0.510$ to $0.501$. \RII{}'s deficit relative to \RO{} shrinks from $0.039$ to $0.031$, as the second amendment predicted, and its gap to \RI{} from $0.027$ to $0.021$ $[0.020, 0.022]$. These are differences between single runs, so we treat them as suggestive. The amendment stated its prediction for the registered prefix, where the warm-up makes Llama scores unusable: \RO{} moves from $0.474$ to $0.779$. With tied embeddings, the BOS row is updated as an output class even though it never appears as input, and in the warm-up runs its norm grows from $0.863$ to $0.896$; this may contribute.

\paragraph{English.} In the main Llama runs under the registered prefix, \RII{} $-$ \RO{} on English is $+0.0003$ $[-0.0002, +0.0008]$ (non-inferior). All three main-run arms are slightly worse on English than the base model ($0.799$ to $0.803$ against $0.788$).

\paragraph{Other BPB views.} The registered sliding-window BPB, which scores whole documents, orders the Nepali arms the same way (Llama rerun $0.424$, $0.437$, $0.464$; Qwen $0.459$, $0.515$, $0.525$). In the BOS-consistent rerun, FLORES Nepali BPB is $0.607$, $0.617$ and $0.626$ for \RO{}, \RI{} and \RII{}; the rerun's three held-out differences match the separator diagnostic of the main runs ($+0.0121$, $+0.0394$, $+0.0273$), and \RII{} $-$ \RI{} lies between the two earlier values, as the third amendment predicted. At $10^{-4}$, every Qwen arm ends better on English than its base model ($0.862$ to $0.864$ against $0.873$).

\paragraph{A failed prediction of the third amendment.} The third amendment also predicted that scores after BOS and after the end-of-text token would agree within $0.005$. This failed: after the end-of-text token the rerun models score $1.017$, $0.875$ and $1.666$. Score a model after the context it was trained with.

\paragraph{English gains.} \RII{} is better than \RI{} on English by $0.0022$ on both models although English tokens are identical; a likely reason is that English is 74\% of \RII{}'s training tokens but 55\% of \RI{}'s, so it weighs more in \RII{}'s loss.

\paragraph{BOS diagnostic.} On 40 held-out Nepali documents (first 1{,}500 characters), Llama BPB after BOS and after the end-of-text token are 0.720 and 1.865 for the base model, 0.441 and 0.438 for \RO{} of the main runs, and 0.758 and 0.438 for \RO{} of the warm-up runs. The norm of the BOS embedding is 0.863, 0.860 and 0.896 respectively (mean row norm 0.98--0.99). The base model, pretrained with BOS at sequence starts, scores far worse without it, while the continued-pretraining models, trained on fixed-length windows that start at arbitrary tokens, do not need it. The BOS-consistent rerun shows the converse: trained with BOS before every document, its models score far worse after the end-of-text token (Table~\ref{tab:cpt}, sep.\ column). We did not test the mechanism further.

\paragraph{Secondary metrics.} Belebele is near chance for every model. Translation scores are erratic: Qwen \RII{} scores 3.9 chrF++ from English to Nepali, below the untrained base model (6.8). We take the first output line as the hypothesis, which is empty when a model starts with a newline, and we did not measure how often that happens. Qwen's FLORES BPB is almost the same for \RI{} and \RII{} (0.689 and 0.688), although \RII{} is worse on held-out native text. We draw no conclusions from these metrics.

\paragraph{Measured generation speed.} Generation was timed once per model, on GPUs that were also running training or evaluation jobs. The Qwen base model and Qwen \RO{} share tokenizer and architecture, yet differ by 41\% in bytes per second, and the generated text has fewer bytes per token than FLORES (8.1 against 12.3 for Llama \RII{}), so the measured speed also depends on what each model chose to write. With these caveats, \RII{} generates $1.48$ (Llama) and $1.50$ (Qwen) times as many bytes per second as \RI{}, and its generations carry $8.07$ and $7.47$ bytes per token against $5.21$ and $5.07$ for \RI{}. Section~\ref{sec:cpt} reports these together with the deterministic ratio of decoding steps on reference text.

\section{What the repair does not fix}
\label{app:notfix}
A wider word class removes the splits that the regex forces, but BPE can still split inside a syllable: 26\% of \texttt{o200k}'s Nepali tokens and 11 to 13\% of \RII{}'s start with a combining mark. An akshara-aware rule~\citep{kapila2026typedriven,darshana2026wwho} restricted to the Devanagari block would keep English token ids by the argument of Proposition~\ref{prop:lossless}; testing one in a deployed model is future work. Added tokens are a second route past the floor that needs no regex change; they split more words mid-way (\S\ref{sec:floor}), but we have not measured their effect on model quality, and our training runs give no evidence that segmentation of this kind matters for it.
